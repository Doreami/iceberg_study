# Rust Iceberg 自定义索引实现 — 需求与设计分析文档

> **文档目的**：基于 Java Iceberg SDK 的 RowID 实现、Rust Iceberg SDK 的社区现状、以及 Lance 对 RowID 的设计，分析自定义索引实现中哪些是 SDK 缺失功能、哪些是索引需实现功能，并按功能分解给出优先级、工作量评估和并行开发建议。
> 
> **适用范围**：V3 表 only，不考虑 V2→V3 升级兼容性。Fork Rust Iceberg SDK 进行开发，社区未合入的 PR 功能纳入待实现范围。
> 
> **开发人力**：2 人
> 
> **报告日期**：2026-07-01

## 一、核心概念与术语对照

在开始分析之前，明确几个核心概念及其在不同系统中的术语对照：

| 概念                 | Java Iceberg SDK                 | Rust Iceberg SDK            | Lance                          |
| ------------------ | -------------------------------- | --------------------------- | ------------------------------ |
| **行逻辑 ID**         | `_row_id` (field ID: 2147483540) | `RESERVED_FIELD_ID_ROW_ID`  | `_rowid`                       |
| **行物理地址**          | `(file_path, position)`          | `(file_path, row_position)` | `_rowaddr`                     |
| **行最后修改版本**        | `_last_updated_sequence_number`  | 未支持                         | `_row_last_updated_at_version` |
| **行在文件内位置**        | `_pos`                           | `_pos`（待实现，参考 #2746）        | `_rowoffset`                   |
| **RowID → 物理地址映射** | 引擎层实现                            | 无                           | `RowIdIndex`                   |

**关键理解**：

- **RowID 是逻辑标识符**：一旦分配，在行生命周期内保持稳定（引擎层 UPDATE/MERGE 继承旧 ID；SDK 层 Overwrite 重新分配）

- **RowAddr 是物理地址**：`(file_path, row_position)`，Compaction 后会变化

- **索引需要 RowID**：索引记录 `(索引键 → RowID)`，回表时通过 RowID 找到物理地址

- **回表需要 RowAddr**：RowID → RowAddr 的映射是索引回表的关键

## 五、阶段一详细分析

### 5.1 A. `_pos` 列读取

**责任归属：SDK 待实现功能（开发者 A）**

**问题描述**：

`_row_id` 的动态计算公式为 `first_row_id + row_position`，其中 `row_position` 即 `_pos` 列。Rust SDK 目前不支持 `_pos` 列读取。

**参考设计**：

[PR #2746](https://github.com/apache/iceberg-rust/pull/2746) 的实现方案：利用 Parquet 读取器的 `RowNumber` 虚拟列获取行号，与 Java 的 `SupportsRowPosition` / `PositionReader` 做法一致。

**核心实现要点**：

1. 在 `TableScan` 中支持投影 `_pos` 元数据列（field ID: 2147483645）

2. 利用 Parquet 的 `RowNumber` 虚拟列获取行位置

3. 跨批次维护偏移状态

**工作量估算**：

| 子任务               | 代码量估算          | 说明                                |
| ----------------- | -------------- | --------------------------------- |
| 元数据列投影框架          | ~150-200 行     | 在 `scan/arrow.rs` 中添加 `_pos` 投影支持 |
| `RowNumber` 虚拟列集成 | ~150-200 行     | 利用 Parquet 原生能力                   |
| 偏移状态维护            | ~80-120 行      | 跨批次正确处理                           |
| 单元测试              | ~150-200 行     |                                   |
| **合计**            | **~530-720 行** |                                   |

**建议开发者**：开发者 A

### 5.2 B. `_row_id` 列读取（动态计算 + 物理列）

**责任归属：SDK 待实现功能（开发者 A）**

**问题描述**：

索引构建时需要读取每行的 `_row_id`。Rust SDK 目前不支持 `_row_id` 元数据列投影。

**参考设计**：

Java SDK 的 `RowIdReader` 实现双重读取逻辑：

```textile
read():
  value = idReader.read()        // 尝试读物理列
  if value != null → return value // 有物理列 → 直接返回
  return firstRowId + position    // 无物理列 → 动态计算 fallback
```

**核心实现要点**：

1. 在 `TableScan` 中支持投影 `_row_id` 元数据列（field ID: 2147483540）

2. 实现双重读取逻辑：
   
   - 优先：读取 Parquet 物理列 `_row_id`（如果存在）
   
   - 后备：动态计算 `first_row_id + row_position`（依赖 A）

3. 参考 Java 的 `RowIdReader` 实现

**工作量估算**：

| 子任务              | 代码量估算          | 说明                                   |
| ---------------- | -------------- | ------------------------------------ |
| 元数据列投影框架         | ~100-150 行     | 在 `scan/arrow.rs` 中添加 `_row_id` 投影支持 |
| `RowIdReader` 实现 | ~150-200 行     | 双重读取逻辑（物理列优先 + 动态计算后备）               |
| 与 `_pos` 列联动     | ~80-120 行      | `_row_id` 依赖 `_pos` 计算               |
| 单元测试             | ~200-300 行     | 覆盖有/无物理列两种场景                         |
| **合计**           | **~530-770 行** |                                      |

**依赖**：A（`_pos` 列读取）完成后

**建议开发者**：开发者 A

### 5.3 C. RowID → RowAddr 映射（回表定位）

**责任归属：索引需实现功能（开发者 B）**

**问题描述**：

索引存储 `(索引键 → RowID)`，回表时需要将 RowID 转换为物理地址 `(file_path, row_position)`。Rust SDK 没有内置的 RowID → RowAddr 映射。

**参考设计**：

Lance 使用 `RowIdIndex` 将 `_rowid` 映射到 `_rowaddr`：

> An index of row ids. This index is used to map row ids to their corresponding addresses. These addresses correspond to physical positions in the dataset.

Lance 区分 `_rowid`（逻辑 ID，稳定）和 `_rowaddr`（物理地址，Compaction 后变化）。

**核心实现要点**：

1. 维护 `RowID → (file_path, row_position)` 映射表（外部 KV 存储，如 RocksDB）

2. 索引构建时填充映射

3. 回表时查询映射获取物理地址

**工作量估算**：

| 子任务      | 代码量估算          | 说明                           |
| -------- | -------------- | ---------------------------- |
| 映射存储接口定义 | ~100-150 行     | KV 存储 trait（RocksDB/Sled 实现） |
| 映射构建逻辑   | ~150-200 行     | 索引构建时填充映射                    |
| 映射查询逻辑   | ~50-100 行      | 回表时查询                        |
| 单元测试     | ~150-200 行     |                              |
| **合计**   | **~450-650 行** |                              |

**建议开发者**：开发者 B

### 5.4 D. Deletion Vector 感知

**责任归属：索引需实现功能（开发者 B）**

**参考设计**：

Rust SDK 已支持删除文件读取（位置删除和等值删除）。索引需在构建时调用删除文件过滤逻辑。

**核心实现要点**：

1. 索引构建时过滤已删除行（读取删除向量，跳过标记删除的行）

2. 查询时过滤已删除行（回表前检查行是否已被删除）

### 6.3 H. UPDATE 后索引更新（RowID 继承）

**责任归属：SDK 待实现 + 索引需实现（A + B 协作）**

**问题描述**：

UPDATE 在 Iceberg 中是 DELETE + INSERT 的组合。引擎层 UPDATE 时，新行应**继承旧行的 RowID**。但 Rust SDK 目前：

- 无行级 UPDATE 能力

- 无 RowID 继承机制

**参考设计**：

Java 引擎层 UPDATE 时显式读取旧 `_row_id` 并写入新文件。SDK 层的 `OverwriteFiles` 是 DELETE + INSERT，会给新行分配新 RowID。

**核心实现要点**：

**索引侧（开发者 B）** ：

1. DELETE 部分：从索引中删除旧条目（同 G）

2. INSERT 部分：新行获得新 RowID，索引插入新条目

3. 代价：无法追踪行级血缘（新旧行无法关联，因为 RowID 变了）

**SDK 侧（开发者 A，如需支持 RowID 继承）** ：

1. 在 SDK 写入层支持显式指定 RowID

2. 引擎层 UPDATE 时读取旧 RowID 并写入新行

**工作量估算**：

### 6.4 I. Compaction 后索引重定向（Remap）

**责任归属：SDK 待实现 + 索引需实现（A + B 协作）**

**问题描述**：

Compaction 重写数据文件后，行的物理位置（`file_path`, `row_position`）发生变化。索引中的 RowID → RowAddr 映射失效，需要重定向。

**参考设计**：

**Lance 方案**：通过 Stable Row ID 解决：

> When a dataset is created with stable row IDs enabled, each row is assigned a unique auto-incrementing u64 identifier that remains constant throughout the row's lifetime, even when the row's physical location (row address) changes.

**Java 方案**：通过 `newRewrite()` + `schemaWithRowLineage()` 显式投影保留 `_row_id` 物理列。

**核心实现要点**：

**索引侧（开发者 B，方案一，推荐）** ：

1. 检测 Compaction 操作（快照类型 `replace`/`overwrite`）

2. 获取新旧文件列表

3. 删除旧文件的映射条目

4. 扫描新文件，重建 RowID → RowAddr 映射

**SDK 侧（开发者 A，方案二，可选）** ：

1. 扩展 Rust SDK 的 `rewriteFiles` 支持 `schemaWithRowLineage()`

2. 确保新文件包含 `_row_id` 物理列

3. 索引只需更新映射（无需重新扫描）

**工作量估算**：

| 新旧文件列表获取           | ~100-150 行       | 从 Manifest 中提取                   | B   |
| 映射清理 + 重建          | ~150-200 行       | 删除旧条目，插入新条目                      | B   |
